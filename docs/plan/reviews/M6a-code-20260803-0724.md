# M6a code review — Codex + independent reviewer, 2026-08-03

Two independent passes over the milestone branch (`git diff main...HEAD`), run in the
verify phase: `./scripts/codex-review.sh code 6a`, and a fresh-context reviewer agent given
the charter, the invariants, the two ADRs, and the plan review — and told to hunt for the
failure modes in the verify checklist rather than for style. Distilled from both raw
transcripts, which are gitignored because a reviewer quotes every file it read.

**Codex's verdict:** *"I would not close M6a with findings 1–3 unresolved."*

Fourteen findings in total: six from Codex, three from the reviewer agent, four from
self-review, and one — the missing regression test for Codex's finding 3 — from mutating
the fixes afterwards. **Nothing was rejected.** Twelve were fixed, one was fixed partially
with the remainder deferred, and one is documented rather than fixable.

Both reviewers independently re-derived the bfloat16 exactness claim and re-enumerated the
`(device, dtype, probe)` matrix, and both found the resolver itself correct. Every defect
they did find was one level up: in how a correct answer was *reported*, or in what happened
when the machine was broken in a way no test had constructed.

---

## The three that mattered

### 1. Critical — `probe_runtime` promised never to raise and caught only `ImportError`

`runtime.py`'s contract is that probing is total: a machine with no Torch, no GPU, or a
broken ROCm stack is a fact to record, not an exception for every call site to handle. The
import was guarded with `except ImportError`.

A ROCm build with a missing or mismatched shared library raises **`OSError`** from the
dynamic loader — and that is precisely the environment failure this milestone exists to
diagnose. Codex injected `OSError("libtorch_hip.so: undefined symbol")` and got an uncaught
traceback where the charter requires an actionable diagnostic. Reproduced before accepting.

The existing "never raises" test could not have caught it: it probed *this* machine, whose
Torch is healthy, so it exercised only the path that already worked.

**Fixed** — `except Exception`, with the failure recorded as `TypeName: message`. Three new
cases (`ImportError`, `OSError`, `RuntimeError`) shadow `torch` on `PYTHONPATH` with a
module that fails on import, which makes them deterministic on any machine instead of
depending on which environment runs the suite.

### 2. High — `doctor`'s `gpu` line reported WARN for the failure its own docstring calls FAIL

Found by the reviewer agent. `doctor.py`'s module docstring is explicit that a Torch with no
HIP version is a **failure**, because in this project Torch comes only from the AMD index,
so a CUDA or CPU-only build means the per-package routing stopped working — the exact silent
failure M6a exists to prevent.

`_check_gpu` decided WARN-versus-FAIL on `cuda_available` and never on `hip_version`. On
this host a CUDA build reports no device, so it took the WARN branch — while printing
`unavailability()`'s own text saying the routing was broken:

```
   torch: fail  2.9.1+cu128 reports no HIP version, so this is a CPU-only or CUDA build…
   gpu  : warn  2.9.1+cu128 reports no HIP version, so this is a CPU-only or CUDA build…
```

Same sentence, two severities. `_check_torch` had the priority right; the two had disagreed
since they were written. `overall_status` still rolled up to FAIL, which is why nothing
noticed — but anything reading a *specific* check out of `doctor --json` got the wrong
answer, and `TestGpuChecks` asserted the `torch` line for that probe and never the `gpu` one.

**Fixed**, with a regression test that asserts both lines.

### 3. Medium — an explicit `device: cpu` recorded the GPU's name

`RuntimeResolution.provenance()` copied `probe.device_name` unconditionally. The probe knows
the name whenever the machine *has* a GPU, so a deliberate CPU run on the target host
produced:

```
device='cpu'  device_name='Radeon 8060S Graphics'  dtype='float32'
```

False provenance, and headed for M6b's ASR cache key under INV-08. The existing tests
covered the CPU-*fallback* case only, using an absent-Torch probe, which could never have
exposed it — the probe had no device name to leak.

**Fixed.** And then caught again: a mutation run showed the fix had shipped **without a
regression test**, so reverting it left all 204 tests green. That is the same omission as
the finding itself, one level up, and it is the reason the mutation pass exists.

## Also fixed

### 4. Critical (Codex) — two subprocess tests ran GPU kernels inside the default suite

`conftest.py`'s `no_torch_import` fixture watches the *parent* process's `sys.modules`, so a
subprocess is the one place it cannot look — and two tests spawn one: the real-probe test in
`test_runtime.py` and the installed-console-script test in `test_cli.py`. Neither was marked
`host_smoke`. On `.venv` nothing happens because there is no Torch; on `.venv-rocm` the suite
the gate calls CPU-only was launching real HIP kernels.

The reviewer agent raised the same thing at lower severity, noting the safety was
"environmental rather than self-enforced". Codex is right that this is the stronger reading:
the fixture's honest boundary is documented, and two tests sat on the wrong side of it.

**Fixed** by shadowing `torch` on the child's `PYTHONPATH` — which also converts both tests
from environment-dependent to deterministic. The real-machine probe moved to `host_smoke`,
where GPU work is the point.

### 5. Medium (reviewer) — `doctor` silently dropped the resolver's warnings

`RuntimeResolution.warnings` is documented as "not decoration — the spec requires it to be
prominent". `_check_resolution` never read it. On a GPU whose BF16 fails and whose float32
works, `auto` resolves to `cuda:0 / float32` *with a warning*, and the line an operator most
wants reported a clean `ok`. Grep confirmed the field was read nowhere in `src/`.

### 6. Medium (Codex) — `record_runtime` overwrote what its docstring called a bug

The docstring said two stages disagreeing "would be a bug worth failing on"; the body
assigned. Once M6b records runtime provenance, a disagreement would produce an
authoritative-looking report carrying only whichever stage wrote last — with the
disagreement, the thing worth knowing, gone. Now it raises; recording the *same* runtime
twice is still fine.

### 7–8. Medium/Low (self) — `_resolve_dtype`'s `auto` path returned float32 unproven

The GPU branch was `if bfloat16 in gpu_dtypes: … else float32`, without consulting
`permits()`. Correct for today's two-entry `SMOKE_DTYPES`; the day a third is added and a
device passes only that one, `auto` would return **unproven** float32. A trap laid for M6b
rather than a bug today. It also made `SMOKE_DTYPES`' "in preference order" comment a claim
the body did not honour — the docstring-exceeds-body pattern M1's closeout names.

### 9. Medium (self) — the boundary guard was a source-grep

`test_no_default_check_measures_the_real_machine` scanned its own file's text for
`run_checks(` calls lacking `probe=`. Defeated by a call split across lines, and silent about
every other file. Replaced with an autouse fixture that makes `probe_runtime` raise, so a
forgotten injection fails on every environment rather than only on the one with a GPU.

### 10. Low (self) — the AMD allowlist was partly circular

Three of the five versions in `EXPECTED_AMD_PACKAGES` were *discovered* by the resolver
rather than chosen, so asserting the lock against them proved the lock equalled itself. Now
cross-checked against the `==` pins in `pyproject.toml`, which are the independent statement
of intent.

### 11. Low (reviewer) — a test opened the real `/dev/kfd` to obtain a path constant

Every field of the result was discarded and overridden; `KFD_NODE` was already imported.
Harmless, but it contradicted the file's own stated pattern and performed a real device open
on the target host.

### 13. Low (Codex) — the `## Working plan` section had become false

It named `probe_torch`, `probe_cpu_bf16` and `TorchProbe` — none of which survived the
restructure — cited test identifiers that no longer existed, and repeated the "newest build
on the index" claim that ADR-0025 had already corrected. It is a scratch section replaced at
closeout, but Codex is right that until then it is exactly the repository memory a future
implementor would trust. Corrected in place, with a note saying so.

## Fixed partially, remainder deferred

### 12. Medium (Codex) — the FHS sdist build has no regression test

The charter claims `rocm[libraries]` builds at install time in the FHS shell. The evidence is
a one-time install transcript; `test_setuptools_is_not_constrained_below_70_2` checks a
constraint, not a build. The `host_smoke` tests run an already-populated `.venv-rocm` and
would stay green if the FHS toolchain were removed tomorrow.

Accepted as stated. Proving it end to end means a network install taking minutes, which the
offline gate cannot do and should not try to. What *is* now protected is the concrete
regression Codex names: `test_the_fhs_shell_still_carries_the_build_toolchain` asserts the
compiler, cmake, make, ninja and pkg-config are still in `targetPkgs`. The build itself is
re-proved whenever someone rebuilds the ROCm environment, and the transcript is in the
closeout. **Recorded as a known limitation rather than closed.**

## Documented rather than fixed

### 14. (Codex) — the lock pins versions, not bytes

Every one of the eight AMD artifacts is recorded in `uv.lock` with a URL and **no hash**,
where every PyPI artifact in the same lock carries a sha256. The AMD index publishes none. So
a re-upload at the same version would be invisible to `uv lock --check` and to us, and the
charter's word "reproducible" overstates what is guaranteed.

There is no mitigation short of vendoring three gigabytes of wheels, which this repository
must not contain. Recorded in ADR-0025's consequences, and
`test_the_amd_index_publishes_no_hashes_so_the_lock_pins_versions_not_bytes` asserts the
asymmetry — so the day AMD starts publishing hashes, the test fails and the paragraph gets
rewritten.

## What the reviewers agreed was sound

Both re-derived these independently rather than taking them on trust, which is why they are
worth recording:

- The bfloat16 smoke operands: all four inputs and all four products are exactly
  representable in an 8-bit significand, so comparing for equality rather than within a
  tolerance is legitimate.
- The full `(device, dtype, probe)` resolution matrix, enumerated by hand against the spec's
  five rules. No cell wrong, no silent downgrade.
- `probe_runtime`'s exception paths: every one returns a probe claiming no more than it
  measured.
- `conftest.py`'s `no_torch_import` fixture: correctly scoped to *newly* resident, correctly
  exempting `host_smoke`.
- The bidirectional lock assertion, which the reviewer agent specifically noted breaks on a
  legitimate version bump — by design.

## The pattern worth carrying to M6b

Every defect found here was in the layer *above* the logic: a correct resolution reported at
the wrong severity, a correct probe whose failure path was never constructed, a correct
decision recorded with a field that did not apply. The resolver — the part that looked
hardest and got the most design attention — was right in both reviews.

That is the third milestone running where the valuable finding was not "the rule is wrong"
but "the thing being asserted is adjacent to the rule". M5's review found a test asserting a
normalized share instead of the applied gain; this one found a `gpu` check asserting
`cuda_available` instead of the build identity its own docstring named.

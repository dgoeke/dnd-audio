# M7a code review — 2026-08-04 21:09

**Reviewer:** independent Codex CLI, read-only review of the milestone branch against `main`,
plus a fresh-context reviewer agent and the verifying agent's own pass
**Verdict:** *not ready to close.* Ten findings from Codex, one from the reviewer agent, four
from the verifier. **Two P0.** All fixed except two explicitly deferred.

This review exists because **M7a was closed without a verify phase.** The first code review
ran at 19:11; the commit fixing its eleven findings landed at 19:43; the milestone was closed
at 20:02. No independent pass ever saw the final code, `STATE.md` never held `verified`, and
the closeout's reported gate run ("2 640 passed") does not match what HEAD produces (2 629).

## P0 findings

1. **`archive verify --report` overwrote an immutable source recording.** The CLI's INV-01
   guard on the report path was written as `if session_dir is not None`, and `verify` and
   `restore` are remote-only by design — they never have a session directory, and both accept
   an operator-supplied `--report`. So `archive verify --session-id X --report
   SESSION/raw/tx-a/DJI_01.WAV` replaced 50 bytes of WAV with 637 bytes of JSON. Reproduced
   end to end. This is the backup tool destroying the thing it exists to protect, through a
   documented flag, on the project's first hard rule.
   **Fixed** — the guard is keyed off the report path itself, walks every session above it,
   and runs *before* the operation instead of after, so an expensive `verify` is not paid for
   and then refused.

2. **One `503 Slow Down` made a session permanently unarchivable.** `put_object` opened the
   body once and `_call` retried the same thunk. A real request transmits the body before it
   can be told 503, so the handle is at EOF on the retry; botocore computes `Content-Length`
   from the current position and PUTs **zero bytes**. The readback catches it and no manifest
   is committed — but the empty object now occupies an immutable content-addressed key, and
   `_publish` refuses to overwrite an existing object, so every later `archive upload` fails
   on that entry with `archive_readback_mismatch` forever. There is no delete command, by
   design. Reproduced: three successive uploads, all fatal.
   **Fixed** — the thunk opens the file per attempt.

## Why neither was visible

**Nothing in the suite executed `_run_archive`.** `tests/test_cli.py` invoked `archive
--help` and an unconfigured `archive list`, which exits at `load_archive_config` above
everything interesting; every other archive test called `run_upload`/`run_restore` directly.
So the CLI's INV-01 guard, its protected-root wiring, its report path and its exit codes were
carried by nothing.

Worse, the test *named* as the regression guard for the first review's P0 — the CLI failing
to pass `protected_session_dirs` — has a docstring reading "This drives the actual command"
above a body that asserts on `_sessions_above` in isolation and never invokes anything.
Deleting the wiring left it green. P0 #1 above was sitting in the same untested block.

Found independently by the Codex reviewer and by the fresh-context reviewer agent.
`TestTheArchiveCommandsRunAndAreGuarded` now drives the real commands against a fake bucket,
with a positive control so the refusals cannot be refusing everything. Both P0 fixes were
mutation-checked by deletion.

The retry tests could not fail either: `RecordingClient` raises from `_record`, before it
touches `Body`, so the second attempt found the handle at position zero. That is the same
shape as the `max_attempts` finding from the first review, where the test asserted the
literal string that encoded the bug.

## P1 findings

3. **Library versions were part of the manifest identity.** `_identity()` compared the whole
   recipe including `zstandard_version` and `libzstd_version` — which `ArchiveCodec.describe`
   has always documented as description rather than identity. An ordinary `uv lock --upgrade`
   therefore made every already-archived session report `divergent` and made `upload` fail
   fatally, telling the operator to choose a new session id or restore from the archive. The
   first review's `track_id` finding is what put the recipe in the comparison; it was drawn
   one field too wide. **Fixed**, with both halves tested — a version bump is idempotent
   success, a changed level is still divergent.

4. **Multipart recovery lost orphans two ways.** `_record_upload` sat above the `try`, so a
   failure writing the state file left a created upload with no record and no abort — the
   exact billable orphan the record prevents, produced by the mechanism meant to prevent it.
   And the record held a single id, so after a *failed* abort the next upload at that key
   overwrote it, permanently losing the id of something still billing. **Fixed** — the record
   holds every unaborted id and is written inside the try; the legacy single-id shape is still
   read, because a record on a real machine names an upload that is billing right now.

5. **`list` called things committed that were not.** Any key ending in the manifest filename
   at any depth was read as a session whose id came from the first path component, and the
   only content check was "not zero bytes", so a one-byte `{` was a committed session.
   **Fixed** — the key must be exactly `manifest_key(session_id)`, and the size floor is
   derived from `RESTORE_INSTRUCTIONS`, which every manifest carries verbatim.

6. **`status` overstated twice.** It inventoried the sources, made a network round trip, and
   reported on a directory that may have moved underneath it. And `_upload_report_says_verified`
   read `operation`, `status` and `verification` and nothing else, so a report left by an
   archive of a *different* session, or of an earlier manifest for this one, vouched for bytes
   it had never seen. **Fixed** both; the history claim now requires the report to name this
   session and this manifest digest.

   The first fix was written twice. The obvious one — build the source set first and
   `verify_unchanged` afterwards, as `upload` does — doubles the work, because
   `verify_unchanged` re-walks and re-hashes, and `status` is the one operation this charter
   calls *cheap*: it would have hashed a four-hour session twice to tighten a claim already
   labelled non-authoritative. Building the inventory **after** the network read closes the
   same window at no cost, and `status` writes nothing so it needs no INV-01 exit check.

   **And the test for it passed for the wrong reason.** It uploaded, then added the file it
   was going to mutate, then uploaded again — but the second upload diverges on the added
   file and never commits, so `status` reported `divergent` no matter which order the code
   read in. A mutation check caught it: with the ordering reverted the test stayed green. It
   now writes and inspects the file before the only upload, and asserts a `committed`
   positive control first. Same failure this whole review is about, committed while fixing it.

## P2 findings

7. **A long session id was uploadable and not restorable.** Restore staged under a directory
   named from the encoded session id. Object keys have a 1 024-byte budget, so a 300-character
   id uploads perfectly and then produces a staging basename past the 255-byte filename
   component limit. Locks and multipart records were converted to digest names after the first
   review; this one was missed. **Fixed**.

8. **Rolled-back restores reported files that exist nowhere.** Entries staged before a failure
   kept the outcome `restored` while the staging tree was deleted and the destination left
   untouched. **Fixed** — they are `skipped`.

9. **Destination refusals carried absolute paths** into the report, which the completion gate
   forbids as local machine identity. **Fixed** — the final component is named instead, which
   loses nothing: there is one destination per invocation and the operator typed it.

10. **An unreachable guard.** `_require_current_manifest` checked `isinstance(document, dict)`
    *after* calling `.get` on it. **Fixed** by ordering.

## Deferred, with reasons

- **A file replaced at the same path between inspection and archiving is accepted, and its
  copied `inspection` block then describes the old file.** `_require_current_manifest` checks
  only `config_hash` and `_require_nothing_vanished` checks only presence. The archive itself
  stays correct — the original digest is measured from the actual bytes, so restoration is
  exact — and the bounded inspection identity is decoration. Recorded rather than fixed:
  closing it means re-hashing every source against the inspection manifest, which is a second
  full pass over a session for a decorative field.
- **The composed memory test substitutes `WatchedStorage`,** so the "staged reads interleave
  with upload calls" boundary is asserted about the test's own loop rather than about
  `SpacesStorage`. The real adapter hands boto3 a file handle and the multipart path reads
  fixed-size chunks, both bounded by inspection, and the host smoke exercises them for real —
  but this specific boundary has no executed proof over production code.

## Rejected

- **The codec freeze digest is self-captured** rather than derived from an independent `zstd`
  CLI run. ADR-0037 deliberately rejected shelling out, and the parametrized level and
  checksum-flag tests prove the freeze can fail, which is what a drift freeze needs.

## What this review changed about the work, beyond the fixes

The first review's closing line was that the milestone's habit should be "if a test claims to
prove a specific line matters, delete that line once." The commit that acted on that review
then shipped a test whose docstring claims it drives the CLI above a body that does not — and
a P0 in the lines it claimed to cover. The habit has to be applied to the fixes, not only to
the code being fixed.

The concrete structural lesson is narrower and more useful: **every layer needs a test that
enters through its own front door.** Nine test files, 261 archive tests, and complete coverage
of the runner did not compensate for zero tests that ran a command.

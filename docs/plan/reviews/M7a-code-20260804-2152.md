# M7a code review — 2026-08-04 21:52

**Reviewer:** independent Codex CLI, read-only review of the milestone branch against `main`,
run **after** the second review's fixes were committed at `8ce468d`
**Verdict:** *not ready to close.* Ten findings — four critical, five high, one in the spec.
**Eight fixed, one partly rejected on measurement, one rejected on cost.**

This is the pass the milestone never got the first time: a review of the code as it actually
stands after the fixes, rather than of the code that preceded them. It found a defect **in
the second review's own P0 fix**, which is the argument for running it.

## Fixed

1. **The raw-write guard failed open — in the fix for the last review's P0.**
   `_reject_report_inside_raw` walked every session above the report path and wrote
   `continue` when a `session.yaml` would not parse, beneath a comment asserting that unknown
   roots are "unknown, not permissive". Continuing is exactly permissive. Corrupting a
   session's YAML was enough to make `archive verify --report SESSION/raw/tx-a/DJI_01.WAV`
   overwrite the recording again — the same P0, through the guard written to stop it.
   **Fixed** — a session that contains the report path and cannot be parsed is a refusal.
   The only session reaching that branch is one containing the report, so nothing unrelated
   is blocked.

2. **A manifest could redirect verification and restore to another session's audio.**
   `_read_remote_manifest` schema-validated the document and checked nothing about whose it
   was, so a valid manifest for session B at session A's key made `verify A` and `restore A`
   operate on B while reporting A — and every digest matched, because they were B's digests.
   Recovery reading correct bytes for the wrong session does not look like a failure.
   **Fixed** — the manifest must name the session it was fetched for, and every entry's
   object key must live under that session's own prefix. The reviewer also caught that a test
   added by the *previous* fix used an object key under a different session's prefix, which
   would have codified the hole; that fixture now builds the canonical key.

3. **`archive list` called large garbage a committed session.** The size floor derived from
   `RESTORE_INSTRUCTIONS` catches truncation and nothing else. **Fixed** — `list` now
   downloads and parses each manifest, checks it belongs to the key it sits at, and reports
   its digest, which is the "manifest identity" the charter asks for. The retrieval cost is
   one 128 KiB-billed object per session and the operator is told the count.

4. **Reports were still not mandatory.** `load_session_config` sat outside the reporting
   boundary in both `run_upload` and `run_status`, so the most ordinary operator error —
   the wrong directory — raised instead of leaving a report. **Fixed.**

5. **Failure reports carried only the successful prefix.** The object that actually failed
   appeared in `errors` but not in `objects`, and the entries never attempted appeared
   nowhere, so the scope of a partial upload had to be reconstructed by subtracting two
   lists. **Fixed** — the failing entry is `failed`, the remainder are `skipped`, and every
   entry in scope has an outcome. This also required fixing what `partial` means: it was
   `PARTIAL if results else FAILED`, which once every failure populates `results` would have
   called a run that died on its first file a partial success. It now asks whether anything
   reached the bucket.

6. **Absolute paths leaked into durable reports.** `_as_error` passed `str(exc)` through, and
   a real `ENOSPC` is `[Errno 28] No space left on device: '/home/…/tx-a/x.zst'`. The
   destination messages had been fixed by hand; this is the one nobody writes. The existing
   ENOSPC tests inject an exception with no `filename`, so they could not see it. **Fixed** —
   every absolute path in a message is reduced to its final component, which keeps the
   actionable half.

7. **Concurrent restores shared one staging tree.** The name derives from the session and the
   destination's parent and was blindly `rmtree`-d at the start, so two restores of one
   session beneath one directory could delete each other's half-written files, or a
   track-scoped run could publish what a whole-session run had staged. **Fixed** — an
   existing staging tree is a refusal, which turns a corruption into an error and makes a
   tree left by a hard kill something the operator is told about.

8. **The spec's "not a third-party service" claim was false.** INV-06 and the spec contrasted
   the archive bucket with "a third-party service". DigitalOcean operates that bucket; it is
   a third party. The prohibition that actually holds — and the one INV-06 exists to enforce
   — is third-party *processing*: the destination stores opaque compressed bytes, decodes
   none of them, and returns them unchanged, which is why a full readback can prove anything
   at all. **Fixed** in the spec, INV-06 and ADR-0035. A rule stated more broadly than it is
   true gets ignored the first time it is inconvenient.

## Partly rejected, on measurement

9. **"Remote verification can accept unverified trailing bytes."** The reasoning was sound —
   the decoder stops at the end of one frame, so the compressed digest covers only what it
   pulled — but the conclusion does not hold when measured: libzstd reads ahead far enough to
   meet the trailing bytes and refuses them as an unknown frame descriptor. A valid frame
   followed by anything is already rejected, one layer lower than the reviewer expected.

   The readback now drains to EOF regardless. It costs one `read` returning empty per object
   and makes "the whole object was downloaded and checked" true by construction rather than
   true because of a decoder's buffering. The test asserts the property — refused, not
   accepted — rather than which layer refuses.

## Rejected, on cost

10. **"Upload does not reverify sources after the manifest commit."** True as stated: the
    last `verify_unchanged` runs before the manifest PUT, not after it. Rejected because
    `verify_unchanged` re-walks and re-hashes the entire session, so closing a window that is
    the duration of a ~2 KB PUT would double the hashing cost of every upload of a
    hundred-gigabyte session. The charter's numbered protocol puts the recheck at step 8 and
    the manifest at step 9, and the runner's docstring says the same — this is the documented
    order, not a gap in it. The meaningful claim is "nothing this run did modified a source
    before it committed", and that is what the existing check makes.

    The reviewer's related observation about `multipart_part_bytes` accepting up to 5 GB is
    noted in the closeout as a deferred hardening: a part is held in memory to be re-sendable
    on retry, so the configurable ceiling bounds a real allocation.

## What this review changed about the work, beyond the fixes

The second review's closing lesson was that every layer needs a test entering through its own
front door. This one adds a sharper one: **the fix for a P0 is itself unreviewed code, and it
is written under exactly the conditions that produce P0s** — late, in a hurry, by someone who
has just been told they were wrong. Finding #1 is that, precisely: a guard whose comment
argues for failing closed and whose code fails open, shipped in the commit that closed the
original hole.

Three reviews have now each found defects the previous one's fixes introduced or missed. The
useful conclusion is not that more reviews are needed indefinitely, but that a milestone's
*last* commit deserves the same scrutiny as its first, and that the verify phase is where
that happens — which is the phase this milestone originally skipped.

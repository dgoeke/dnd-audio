# M6a plan review — Codex, 2026-08-03

Independent critique of the working plan in `../milestones/M6a-rocm-environment.md`, run
before any code existed (`./scripts/codex-review.sh plan 6a`). Distilled from the raw
transcript, which is gitignored because a reviewer quotes every file it read.

**Verdict:** *"I would not approve this plan yet. The architecture is directionally sound,
especially the pure resolution/impure probing split, but four items would fail or only
appear to satisfy the completion gate."*

Ten findings. **Nine accepted**, one accepted in substance while its remedy was narrowed.
Two were confirmed empirically rather than argued: finding 1 was independently reproduced
by a parallel agent that had already hit the same wall, and findings 7 and 8 were checked
against the upstream metadata before being acted on. The findings changed the dependency
set, restructured the probe, added two CLI options, and reordered the milestone.

---

## Accepted

### 1. Critical — `[tool.uv.sources]` cannot route a transitive-only requirement

The plan routed `torch` to the AMD index and expected torch's own `rocm[libraries]`
requirement to follow it there. It does not. uv applies the sources table when it resolves
a name it was *asked for*, not when it discovers one inside another package's metadata, so
`rocm[libraries]==7.13.0` was looked up on PyPI — where `rocm` is an unrelated placeholder
at 0.1.0 — and resolution failed.

**Confirmed independently and empirically.** A parallel agent working the lock had already
reached the same failure, added `rocm = { index = "amd-gfx1151" }`, watched it change
nothing, and verified with a clean isolated reproduction: a project depending only on
`requests`, with the transitive-only `urllib3` routed to a different explicit index, still
locked `urllib3` from PyPI. The sources entry was silently ignored — no warning, no error,
just the wrong registry in the lock.

**Accepted.** Torch's AMD-only requirements are now direct members of the `asr-qwen` group
as well as entries in the sources table. This is what uv's own PyTorch/ROCm guide
prescribes, and the reason it does is the finding above.

The uncomfortable part is the failure mode rather than the fix: an ignored routing entry
does not announce itself, so a lock that silently used PyPI would look exactly like a lock
that worked. That is what finding 5's allowlist assertion is for.

### 2. Critical — the INV-05 proof contradicted the installation step

The plan installed the group with `uv sync --group asr-qwen` and then claimed, as proof,
that the gate "runs `--no-sync` against a venv that has none". Both cannot be true: after
that sync the ordinary suite would run with torch installed, and the gate neither removes
it nor demonstrates that a default sync excludes it.

**Accepted.** The intent had been a separate environment all along and the plan failed to
say so, which is the same defect as not having one. Now explicit: the group installs into
`UV_PROJECT_ENVIRONMENT=.venv-rocm`, `.venv` never receives it, and the everyday gate
therefore keeps running the group-absent case rather than proving it once.

The reviewer's second half is accepted too and is the stronger half: proving the *module*
imports no torch is too narrow, because the question is whether any pre-ASR command does.
The subprocess proof now imports `dnd_audio.cli` — which pulls in every runner — and
asserts torch is absent from `sys.modules`. A lock-closure test covers the packaging side
offline, since an actual clean `uv sync` needs the network and cannot live in the suite.

### 3. High — the resolver did not test the combination actually requested

The plan's probe ran one BF16 operation and `validated` required it, then every resolution
consumed that single verdict. Two wrong outcomes follow, and the reviewer is right about
both: an explicit `cuda` + `float32` request would be *rejected* because BF16 failed, even
though the requested combination works; and an explicit `float32` request would be
*accepted* having never been smoke-tested at all.

The charter says an explicitly requested device/dtype combination that fails its smoke test
is rejected. The plan tested a different combination and reported on that one.

**Accepted, and it restructured the probe.** Device availability and per-dtype arithmetic
are now separate: the probe records, per device, which dtypes produced exactly the right
answer, and resolution requires the pair it is about to hand back. `auto` on a GPU whose
BF16 fails but whose float32 works now resolves to float32 with a warning instead of
falling all the way back to CPU — which is both more useful and more honest than the plan's
behaviour.

### 4. High — `doctor` had no user-facing path for a requested device or dtype

`doctor` takes a path and `--json`, and the plan did not touch `cli.py`. So the criterion
"`device: cuda` requested but failing → actionable diagnostic and failure" would have been
demonstrated only by module-level tests, never through the command an operator runs.

**Accepted.** `doctor` gains `--device` and `--dtype`. This also resolves an unease the plan
recorded and did not fix: the resolver's explicit-request paths had no production caller at
all in M6a, and unused production code is how a rule rots between milestones.

### 5. High — the lock test did not prove the ROCm half of its own criterion

The proposed assertion checked torch's registry and version and the absence of `nvidia-*`.
It asserted nothing about any `rocm`, `rocm-sdk-*`, or `triton` artifact, so "the lock
contains the intended AMD Torch **and ROCm artifacts**" could regress while the test stayed
green.

**Accepted.** The test now asserts an exact allowlist in both directions: every package
resolved from the AMD index is one of the expected ones at its expected version, and every
package outside that set resolves from PyPI. Given finding 1, the second direction is the
one that matters — a silently-ignored routing entry shows up there and nowhere else.

### 6. High — the probe M6b inherits was incomplete

Device-node results sat outside `TorchProbe` while `resolve_runtime` consumed only the
Torch half, so M6b could accept a GPU without ever incorporating the `/dev/kfd` and
render-node evidence the spec requires.

**Accepted for the record, narrowed for the rule.** The node results now live in the same
frozen probe, so there is one document to hand M6b rather than two to keep in step. What is
*not* accepted is making node openability a precondition of resolution: successful BF16
arithmetic on the device is strictly stronger evidence than an `open()` on a character
device, and a rule that failed a working GPU because a node glob came back empty would be
inventing a failure. The nodes are recorded and reported; the arithmetic decides.

Its `gfx1151` half is also narrowed. Pinning the target architecture inside a general
resolver would make the rule wrong on any other machine; the `host_smoke` test asserts
`gfx1151` and `doctor` reports it, which is where a claim about *this* host belongs.

### 7. Medium — the dependency floors guaranteed M6b would relock

The plan used `transformers>=4.56` and `accelerate>=1.0`. `qwen-asr` 0.0.6 requires exactly
`transformers==4.57.6` and `accelerate==1.12.0`.

**Verified against PyPI's metadata for that release and accepted.** Both are now pinned to
those exact versions. A floor here would have meant M6b relocking and reinstalling a
multi-gigabyte environment that this milestone exists to settle — the cost lands on the
next milestone, which is where it would have been least visible.

### 8. Medium — the stated reason for the torch version was false

The plan called `2.9.1+rocm7.13.0` the newest build on the index. AMD also publishes
2.10.0 and 2.11.0 for cp312 Linux.

**Verified against the index and accepted.** The version does not change; the reasoning
does, because the reviewer's own observation is the right one — "tested" beats "newest".
ROCm 7.13 is the generation this host already runs a GPU workload on, which is evidence
about the runtime and none at all about a torch version; between three candidates with no
host evidence, a patch release beats two `x.y.0` releases. That is now what the comment
says, instead of a coincidence that was not true.

### 9. Medium — render-node discovery was over-strict

Opening every `renderD*` and failing if any refuses breaks on a host whose *second*,
unrelated GPU is inaccessible — and neither identifies the node backing torch device 0.

**Accepted in effect.** At least one openable render node is a pass; the others are
reported rather than fatal. The generic multi-GPU mapping question stays parked under
OQ-021 rather than being solved here, which is the reviewer's own recommendation.

### 10. Medium — the ledger was already inconsistent

`scripts/check_plan.py` reported ten failures: the working plan cited ADR-0025, ADR-0026
and OQ-021, none of which existed, and the code cited OQ-021 too. Creating them as final
cleanup in step 8 is backwards.

**Accepted without reservation.** This is the working agreement's own rule — an ADR is
written when the decision is made, not when the milestone ends — and the plan had written
it down and then scheduled it last. Registered before any further code.

## What the reviewer got right that no test would have caught

Findings 3 and 5 are the valuable ones, and they are the same shape as M5's plan review
finding about asserting the share instead of the applied gain: in both cases the plan named
a proof, the proof would have passed, and it was measuring something adjacent to the
criterion rather than the criterion. A BF16-only probe deciding a float32 request, and a
lock assertion that never mentions ROCm, are each green-by-construction.

Finding 1 is the one that would have cost the most hours, and it is worth noting that two
independent agents reached it by opposite routes — one by reading uv's index semantics, one
by watching a routing entry get ignored — within minutes of each other.

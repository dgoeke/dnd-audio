## Verdict

Changes requested. M0 does not yet satisfy its completion gate; there are two invariant-level blockers.

## Findings

1. **Blocker — INV-13: an empty report is considered complete and exits zero.**  
   [IngestReport._check_stages](src/dnd_audio/artifacts/report.py:213) only rejects duplicates; it never requires every `StageName`. [ReportBuilder.build](src/dnd_audio/artifacts/report.py:335) silently omits unrecorded stages, while [roll_up](src/dnd_audio/artifacts/report.py:235) returns `complete` for an empty list. The tests explicitly bless both an empty `stages=[]` report and `roll_up([]) == COMPLETE` at [tests/test_report.py](tests/test_report.py:135). I reproduced a fresh builder producing `overall_status="complete"`, zero stages, and exit code 0. This directly contradicts “a status for every stage” in INV-13 and the M0 gate. The model also accepts an explicitly supplied `overall_status` inconsistent with its stages.

2. **High — INV-11: valid configuration can swap transmitter directories and produce wrong speaker attribution.**  
   [TrackConfig](src/dnd_audio/config.py:127) validates `track_id` and `input` independently, and [_check_roster](src/dnd_audio/config.py:276) checks only uniqueness. Swapping the unique inputs of `tx-a` and `tx-f` validates successfully; the resulting mapping says Alice’s `tx-a` reads `raw/tx-f`, while Frank reads `raw/tx-a`. M1 would therefore attribute each recording to the wrong person. “Directory identity is authoritative” is not structural here despite the module’s claim; the input directory and `track_id` must be tied together or identity must be derived from the directory.

3. **High — INV-05: the network fixture does not fully block name resolution.**  
   [_BLOCKED_MODULE_FUNCTIONS](tests/conftest.py:49) omits `socket.gethostbyaddr` and `socket.getnameinfo`, both of which may invoke NSS/DNS. The fixture also provides a blanket `allow_network` bypass at [tests/conftest.py](tests/conftest.py:62), but the gate excludes only `host_smoke`, so an `allow_network` test remains part of the purportedly offline suite. The working plan additionally claims AF_INET/AF_INET6 socket creation is blocked, which the implementation does not do. The existing proof tests only the selected APIs and cannot detect these escape paths.

4. **Medium — the promised deterministic decisions subsection does not exist.**  
   The spec requires provenance and decision subsections to remain semantically stable, and the proof table claims tests compare “provenance and decisions” at [M0-foundation.md](docs/plan/milestones/M0-foundation.md:219). But [IngestReport](src/dnd_audio/artifacts/report.py:203) has no decisions field, and the corresponding test compares provenance only. This was an accepted plan-review finding that only appears implemented.

5. **Medium — recovery override paths are validated but not normalized, breaking INV-08 and risking missed timing evidence.**  
   [RecoveryConfig._check_keys](src/dnd_audio/config.py:250) calls `_validate_relative_path(key)` but discards its normalized return value. I verified that `raw/tx-a/file.wav` and `raw//tx-a/./file.wav` both validate but remain different keys and produce different configuration hashes. Later lookup by a normalized discovered path can also fail to find the configured override. Normalize keys and reject collisions after normalization.

6. **Medium — the atomic-write tests cannot fail on a non-atomic implementation.**  
   In [test_a_failed_write_leaves_the_previous_file_intact](tests/test_determinism.py:75), serialization raises before `write_atomic` is entered. The report version at [tests/test_report.py](tests/test_report.py:285) raises during `build`, also before writing begins. Replacing `write_atomic` with a direct `path.write_bytes(payload)` would still pass these tests. The current implementation looks atomic, but the completion-gate claim is not demonstrated against a regression during the actual write/replace sequence.

7. **Medium — the skipped-test enforcement rail remains fail-open.**  
   [scan_placeholders.py](scripts/scan_placeholders.py:23) recognizes only `mark.skip`, `mark.skipif`, and `mark.xfail`; runtime `pytest.skip`, `pytest.importorskip`, and equivalent mechanisms are invisible. It also checks `reason=` and a milestone/OQ match independently anywhere within a four-line window, so an unrelated test name containing `M6b` can justify a generic reason. Because pytest skips do not fail the gate, these cases can silently satisfy future milestones contrary to the hard rule.

No new unregistered DJI hardware, timing, or model-behavior assumptions were found. I reviewed `main...HEAD`; the unrelated uncommitted edit to `scripts/codex-review.sh` was excluded, and no files were modified.

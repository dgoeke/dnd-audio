---
description: Verify a milestone — run the gate, prove each criterion, and get independent review
argument-hint: "<milestone id, e.g. 0, 2, 6a, 11> [additional context]"
---

**Invocation:** `$ARGUMENTS` — the milestone ID first, then anything else.

Resolve **$0** to its charter under `docs/plan/milestones/`; a bare number means
the M track (`2` is M2). That charter's own ID — `M0`, `M6a`, `M11` — is
what `<ID>` means below. Anything the invoker typed after the ID names something
to scrutinize particularly hard. Add it to the hunt; it never replaces a gate
criterion or lowers the bar for a verdict.

Verify milestone **<ID>**. Your job in this command is to be the adversary of the
code, including code you wrote yourself an hour ago. A milestone is not complete
because it looks complete.

Do not fix anything during phases 1–3. Collect findings first, then triage.

## 1. Mechanical gate

```bash
./scripts/gate.sh
```

Quote the real output. If it fails, stop and go back to implementation. If it
reports skipped checks, each one needs a justification the charter supports.

## 2. Prove every gate criterion

Read the charter's Completion gate. For **each** checkbox, produce:

- The specific test name or command that demonstrates it.
- Its actual output, run now — not remembered, not inferred.
- A one-line statement of what would have to break for that test to fail.

If a criterion has no proof, it is not met. Say so plainly rather than arguing it
is "effectively covered".

## 3. Look for work that only appears done

Check for each of these and report what you find:

- **Tests that cannot fail.** Assertions on constants, `assert x == x`, tests with
  no assertion, tests whose fixture was generated by the code under test.
- **Circular fixtures.** Expected values captured from the implementation's own
  output rather than derived from independent ground truth. This is the single
  most common way a byte-stability or timing test becomes worthless.
- **Weakened assertions.** Tolerances widened, `approx` where exact was specified,
  a test narrowed to make it pass.
- **Placeholders.** `pass`, empty returns, stubs that satisfy a type checker and
  nothing else. The scanner catches annotated ones; you are looking for the rest.
- **Skipped or xfailed tests.** Each must name a milestone or `OQ-` and be
  genuinely blocked, not merely inconvenient.
- **Invariant regressions.** Walk `docs/plan/INVARIANTS.md` and check the ones this
  milestone touches — especially INV-02 (byte stability), INV-04 (exact time
  arithmetic), INV-07 (bounded memory), and INV-09 (mix independent of ASR).
- **Undocumented assumptions.** Anything the code believes about DJI hardware,
  model behavior, or timing that is not registered in `OPEN-QUESTIONS.md`.

## 4. Independent review (required — at least once per milestone)

Commit the branch first, then:

```bash
./scripts/codex-review.sh code <ID>
```

Codex has a genuinely different read on this kind of code; the point of this step
is the findings you would not have generated yourself. Read the whole output.

Then get a second independent pass from a fresh-context reviewer that did not
write the code, using the Agent tool with `feature-dev:code-reviewer`. Give it the
charter path, the invariants file, and the diff range — and tell it explicitly to
hunt for the failure modes in phase 3, not for style.

## 5. Triage

Present one consolidated table: finding, source (gate / self-review / codex /
reviewer agent), severity, and disposition — **fix now**, **defer with an issue
recorded in the charter's closeout**, or **reject with a reason**. Rejecting a
finding is legitimate; rejecting it silently is not.

Fix everything marked fix-now, then re-run phase 1 and the affected proofs.

## 6. Verdict

State either:

- **VERIFIED** — every criterion has a named, executed proof; the gate passes;
  outstanding findings are deferred or rejected with reasons. Set the milestone to
  `verified` in `STATE.md` and run `/ms-close <ID>`.
- **NOT VERIFIED** — list precisely what is missing and what the next step is.

Do not report VERIFIED with caveats. A caveat means not verified.
